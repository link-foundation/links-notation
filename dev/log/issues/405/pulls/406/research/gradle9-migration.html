This chapter provides the information you need to migrate your Gradle 9.x.y builds to the latest. For migrating to Gradle 9.0.0, see the older migration guide first.

As soon as Gradle 11.0.0 ships, no security or bug fixes will be made on any release of Gradle 9. To receive fixes for these versions, see Gradle Security Subscription.

We recommend the following steps for all users:

  1. Try running gradle help --scan and view the deprecations view of the generated Build Scan.

    This lets you see any deprecation warnings that apply to your build.

    Alternatively, you can run gradle help --warning-mode=all to see the deprecations in the console, though it may not report as much detailed information.

  2. Update your plugins.

    Some plugins will break with this new version of Gradle because they use internal APIs that have been removed or changed. The previous step will help you identify potential problems by issuing deprecation warnings when a plugin tries to use a deprecated part of the API.

  3. Run gradle :wrapper --gradle-version 9.9.1 to update the project to 9.9.1.

  4. Try to run the project and debug any errors using the Troubleshooting Guide.

Upgrading from 9.8.0 and earlier

Potential breaking changes

GradleException now carries resolution suggestions

GradleException now supplies the resolution suggestions that Gradle prints beneath a failure, rather than leaving that to a handful of exception subtypes.

It does this by implementing the internal org.gradle.internal.exceptions.ResolutionProvider interface, which subtypes previously implemented directly. GradleException gains getResolutions() from it, alongside the new addResolution(String) and clearResolutions().

This matters only if you had already subclassed GradleException, or one of its public subtypes:

  • If you directly implemented ResolutionProvider on a subclass yourself, you no longer need to, because GradleException already implements it.

  • If you added a getResolutions() method to a subtype that returns anything other than List<String>, this no longer compiles.

  • Similarly, if you added an addResolution(String) or clearResolutions() method to subtypes, they must return void.

  • Custom implementations of addResolution(String), getResolutions(), clearResolutions() should honor the implicit contract between these methods.

Subclasses of ResolveException and ProjectConfigurationException also can no longer override getResolutions(). Those types combine the resolutions added to them directly with the ones contributed by their causes, and an override would silently discard the former. Add resolutions to these types with addResolution(String) instead.

Upgrade to Kotlin 2.4.21

The embedded Kotlin has been upgraded from 2.4.10 to Kotlin 2.4.21.

Configuration Cache and Problems report data format changes

The format of the data embedded in the HTML files of the Configuration Cache report (including when Isolated Projects is enabled) and the Problems report has changed in Gradle 9.9.0. The reports themselves are not affected and look the same when opened in a browser.

This change only matters to tools and scripts that extract the embedded data from the report HTML files. This data is an internal implementation detail of Gradle: it has never been a public API, and its format may change again in any future release, including patch releases, without notice. If you have to extract this data, parse it defensively and expect to adjust your tooling when upgrading Gradle.

To consume problem data in a supported way, use the Problems API bindings of the Tooling API, as described in Tooling API Clients.

There is no supported way to programmatically inspect Configuration Cache problems yet. The following issues track the development of TestKit APIs for this purpose:

  • gradle/gradle#35595: an API for verifying Configuration Cache compatibility and the inputs used by a build.

  • gradle/gradle#38223: an API for verifying whether a Configuration Cache entry was reused, missed, or discarded.

These APIs are intentionally focused on testing use cases. If you extract the report data for other purposes, please comment on these issues and describe your use case.

Runtime problem IDs moved to the predefined problem groups

The remaining problems Gradle reports now use the predefined problem groups, and the legacy groups configuration-usage, daemon-toolchain, jvm-toolchain, packaging, plugin-application, problems-api, scripts, task-selection and validation are gone. Problems with the requested tasks report into Gradle > Invocation. Configuration Cache problems report into Gradle > Configuration Cache and Isolated Projects problems into Gradle > Isolated Projects; they previously shared the legacy validation:configuration-cache group. Problems with the configured build, such as a reserved configuration name, a project with an invalid directory, or several build scripts in one directory, report into Gradle > Build Definition. Problems with how build logic uses the build model, including the contract of project features and misuse of the Problems API itself, report into Gradle > Build Logic.   • Configuration Cache and Isolated Projects problems are named after the kind of problem, for example Error writing value or Cross-project model access, instead of the message in kebab case. Details such as types, members, and projects no longer appear in the name; they remain in the problem’s contextual label.

  • Task selection problems name what Gradle looked for, and a project that cannot be found in a task path has its own name, for example Task not found and Project not found instead of No matches and Selection failed.

  • Names that relied on their legacy group for context now carry it, for example Configuration method call not allowed instead of Method call not allowed, and Reported problem has no id instead of Problem id must be specified.

  • Init invocation problem is now Exclusive task run with other tasks.

  • Project features binds to BuildModel.None is now Project feature binds to BuildModel.None.

  • The updateDaemonJvm task configuration problem is split into two problems, one for missing toolchain download repositories and one for repositories that cannot resolve the requested toolchain.

Builds that move the root project directory now load their settings file

A build can move its root project with rootProject.projectDir. When such a build was started with an explicit project directory, Gradle evaluated the settings file, found no project at that directory, and discarded the settings. It then ran with a single root project at that directory, named after the directory and configured by any build script found there, as if the settings file did not exist. With the Build Cache enabled, it failed with Build cache controller already set instead. The Tooling API always sets a project directory, so every IDE run and every IDE sync was affected.

Gradle now keeps the evaluated settings and selects the root project for the build’s root directory, so these builds load and run as written.

Two consequences are worth checking when you upgrade:

  • A build that silently ignored its settings file now uses it. Configuration problems that were never reached before can surface.

  • beforeSettings, settingsEvaluated and the Evaluate settings build operation each fired twice in the affected case and now fire once. Init scripts and build operation consumers that observed the second firing will see one.

Running Gradle in a directory that is not part of the build now fails

When Gradle is invoked in a directory that lies inside a build’s directory tree, other than the build’s root directory, and is not a project directory of that build, gradle help and gradle with no task names previously discarded the surrounding build’s settings and reported an undefined build:

Directory '/home/user/project/sub' does not contain a Gradle build.

To create a new build in this directory, run gradle init

Gradle now reports that the directory is not part of the surrounding build, and fails:

Project directory '/home/user/project/sub' is not part of the build defined by settings file '/home/user/project/settings.gradle'. If this is an unrelated build, it must have its own settings file.

gradle <task> has always produced this message in the same directory, so Gradle now behaves consistently whether or not you name a task.

The same applies to Tooling API clients that request a model for such a directory without running a task. Such a request previously treated the directory as a separate build with its own root project, or failed with Build cache controller already set when the Build Cache was enabled. It now fails with the message above. Running a task in that directory through the Tooling API already failed this way.

If you hit this failure, pick whichever option matches your intent:

  • Run Gradle from a project directory of the build, or from the build’s root directory.

  • If the directory is meant to be an independent build, give it its own settings file. Running gradle init in the directory creates one for you.

  • If the directory is meant to be part of the surrounding build, add it to that build’s settings file with include.

Two cases are unaffected:

  • Running Gradle in a directory with no settings or build script anywhere in its parent hierarchy still reports an undefined build and still suggests gradle init.

  • Running gradle init in a directory inside an existing build still creates a new build there.

Required input file properties reject absent providers nested in collections

Required task input file properties now fail validation when a provider nested in a plain collection or array (such as a List passed to TaskInputs.files(…​)) has no value. Previously, Gradle silently ignored such absent providers. This applies to TaskInputs.files(…​) declarations and to required @InputFiles properties whose value is such a collection or array. Gradle reports the failure as the Required value isn’t set validation problem.

Passing several providers as varargs, such as inputs.files(providerA, providerB), was ignored in the same way. The collection and varargs forms now fail just like the direct form when the task runs:

build.gradle.kts
val absent = objects.fileProperty() // no value configured

// Failed before this change, and still fails
tasks.register("direct") {
    inputs.files(absent).withPropertyName("p")
    doLast { }
}

// Succeeded before this change, silently resolving to an empty collection; now fails
tasks.register("wrapped") {
    inputs.files(listOf(absent)).withPropertyName("p")
    doLast { }
}

To fix this, make sure every provider in the collection has a value. If the input is genuinely optional, declare it as such with optional() on the TaskInputs.files(…​) registration, or with @Optional on the @InputFiles property. Optional inputs are not affected by this change and continue to ignore absent providers.

Test filters apply to tests that are not declared as methods

Some JUnit Platform engines declare tests on something other than a method. ArchUnit declares rules on fields, and Spek declares scopes. Gradle previously ran such tests unconditionally, whatever test filters were in effect. They are now matched by their enclosing class and the name they are reported with, in the same way as test methods.

A filtered run that used to include these tests by accident no longer does. For example, gradle test --tests "SomeUnrelatedTest" previously ran every ArchUnit rule in the source set as well, and now runs only SomeUnrelatedTest. Review the --tests arguments, filter blocks and include/exclude patterns in your build and CI configuration, because a filtered run may now execute fewer tests than before.

To keep such a test running under a filter, name it or its class in the pattern:

  • --tests "ArchRulesTest" runs every rule declared in ArchRulesTest.

  • --tests "ArchRulesTest.firstRule" runs the rule declared in the firstRule field on its own.

  • Rules grouped with ArchTests.in(…​) are reported as GroupedClass > ruleName, after the class passed to ArchTests.in(…​) and not the field that holds the set. For a set held in a field nested of ArchRulesTest that wraps NestedRules, --tests "ArchRulesTest.NestedRules > nestedRule" runs that rule.

For a test that is not declared as a method, the name after the class is the name its engine reports, not a method name Gradle derives. Engines own these names and may change them in any release, including a patch release. A pattern like ArchRulesTest.NestedRules > nestedRule can therefore stop matching, or start matching something else, when you upgrade ArchUnit or Spek, with no deprecation warning from Gradle. Prefer naming the enclosing class alone where that is specific enough, and treat a pattern that names an individual non-method test as something to re-check on every engine upgrade.

Tests that an engine registers only while a class is executing, as Kotest does, are not affected by this change. Gradle applies filters before those tests exist, so they can still only be selected by their spec class.

See Test filtering for details.

Legacy dependency resolution APIs download artifacts eagerly

The following methods of the legacy ResolvedConfiguration and ResolvedDependency APIs now download the files of all returned artifacts in parallel before returning:

  • ResolvedConfiguration.getResolvedArtifacts()

  • ResolvedDependency.getModuleArtifacts()

  • ResolvedDependency.getAllModuleArtifacts()

Previously, these methods returned artifacts without downloading them, and each artifact’s file was downloaded one at a time when ResolvedArtifact.getFile() was called. LenientConfiguration.getArtifacts() already downloaded the files of the returned artifacts, and now downloads them in parallel as well.

This change makes the artifact download behavior of ResolvedConfiguration and ResolvedDependency consistent with LenientConfiguration, FileCollection, ArtifactCollection, and ArtifactView.

As a result:

  • These methods now fail if any artifact they return cannot be downloaded, instead of failing later when the file of that artifact is accessed.

  • Builds that call these methods without accessing every file may now download artifacts not downloaded previously.

To mitigate this change, consider the following:

  • To inspect the dependency graph without downloading any artifacts, use the ResolutionResult API.

  • To download the artifacts of only some dependencies, use an ArtifactView with a component filter.

  • If you cannot migrate away from the legacy APIs, call ResolvedDependency.getModuleArtifacts() only on the dependencies whose artifacts you need, instead of calling ResolvedConfiguration.getResolvedArtifacts() or ResolvedDependency.getAllModuleArtifacts().

  • To ignore artifacts that cannot be downloaded, use a lenient ArtifactView or LenientConfiguration.getArtifacts(), which omit such artifacts from the result instead of failing.

Neither the legacy APIs nor ArtifactView can download a single artifact of a dependency in isolation.

In general, the ResolvedConfiguration, LenientConfiguration, ResolvedDependency, and ResolvedArtifact APIs are discouraged. They are not compatible with the Configuration Cache and, unlike the modern APIs, do not carry the task dependencies required to build the artifacts they return. Prefer the ResolutionResult, ArtifactView, FileCollection, and ArtifactCollection APIs, described in Artifact Resolution.

The wrapper task preserves existing wrapper properties

When the wrapper task regenerates an existing gradle-wrapper.properties file, it now keeps the values already in that file instead of resetting them to defaults. This applies to the distribution type (bin or all), distributionBase, distributionPath, zipStoreBase, zipStorePath, networkTimeout, validateDistributionUrl, retries, and retryBackOffMs. Values configured on the task or passed on the command line still take precedence.

For example, given this existing file:

gradle/wrapper/gradle-wrapper.properties
distributionUrl=https\://services.gradle.org/distributions/gradle-9.8.0-all.zip
networkTimeout=60000

Running ./gradlew wrapper --gradle-version 9.9.0 previously wrote a -bin.zip URL and networkTimeout=10000. It now writes a -all.zip URL and keeps networkTimeout=60000.

This changes the result for builds and scripts that relied on regeneration to reset these values:

  • A single --no-validate-url run now disables URL validation until you run the task again with --validate-url.

  • An invalid value in the existing file, such as a non-numeric networkTimeout, now fails the task with Invalid value '<value>' for property '<name>'. Previously, the task ignored it and overwrote it with the default.

  • A Wrapper task that you register yourself now writes the default networkTimeout, retries, and retryBackOffMs when you don’t configure them. Previously, only the built-in wrapper task wrote these defaults.

To set a value explicitly, pass the matching option, for example --distribution-type bin, --network-timeout 10000, or --validate-url, or configure the property on the task. The distributionUrl is regenerated for the requested Gradle version, so a custom host is not preserved; pass --gradle-distribution-url to keep one.

See Preserving Existing Wrapper Properties for details.

Deprecation of querying artifact transform outputs from an artifact transform action

Querying the output of one artifact transform from the action of another, without declaring that output as an input of the querying action, is deprecated and will become an error in Gradle 10.

This happens when a transform action resolves a configuration or artifact view that isn’t declared on its parameters, and that resolution requires another artifact transform. A common case is a configuration held by a shared build service.

In the following deprecated example, MakeGreen reads files transformed by MakeRed through a build service:

abstract class FilesService : BuildService<FilesService.Params> {
    interface Params : BuildServiceParameters {
        val files: ConfigurableFileCollection
    }
}

interface Parameters : TransformParameters {
    @get:Internal
    val service: Property<FilesService>
}

abstract class MakeGreen : TransformAction<Parameters> {
    override fun transform(outputs: TransformOutputs) {
        // Deprecated: resolving these files runs MakeRed, which MakeGreen doesn't declare as an input
        val redNames = parameters.service.get().parameters.files.files.map { it.name }
        // ...
    }
}

To fix this warning, declare the files the transform action uses as one of its inputs. Use a parameter annotated with @InputFiles, and set it when registering the transform. In the following example, MakeGreen keeps only the input artifacts that also appear in the resolved configuration. It reads those files after MakeRed transforms them, so it declares them on its redFiles parameter:

val color = Attribute.of("color", String::class.java)

interface Parameters : TransformParameters {
    @get:InputFiles
    val redFiles: ConfigurableFileCollection
}

abstract class MakeGreen : TransformAction<Parameters> {
    @get:InputArtifact
    abstract val inputArtifact: Provider<FileSystemLocation>

    override fun transform(outputs: TransformOutputs) {
        val input = inputArtifact.get().asFile
        // Use the files declared on the parameters, rather than files
        // reached in another way, like through a build service
        val redNames = parameters.redFiles.files.map { it.name }
        if (input.name + ".red" in redNames) {
            input.copyTo(outputs.file(input.name + ".green"))
        }
    }
}

val deps = configurations.dependencyScope("deps")
val resolved = configurations.resolvable("resolved") {
    extendsFrom(deps)
    attributes.attribute(color, "blue")
}

dependencies {
    attributesSchema {
        attribute(color)
    }
    deps("org:bar:1")
    // MakeRed is any transform from "blue" to "red"
    registerTransform(MakeRed::class) {
        from.attribute(color, "blue")
        to.attribute(color, "red")
    }
    registerTransform(MakeGreen::class) {
        from.attribute(color, "blue")
        to.attribute(color, "green")
        parameters {
            // Declare the output of MakeRed as an input
            redFiles.from(resolved.map {
                it.incoming.artifactView {
                    attributes.attribute(color, "red")
                }.files
            })
        }
    }
}

Deprecation of the legacy problem identity API

The incubating Problems API provides a predefined hierarchy of problem groups, available from the Problems service as problems.groups. The API that builds or reads problem identity outside that hierarchy is deprecated. ProblemGroup.create() and ProblemId.create() will be removed in Gradle 11. getDisplayName() on ProblemGroup and ProblemId and ProblemGroup.getParent() will be removed in Gradle 10, and Gradle 10 will not support subclassing ProblemGroup or ProblemId. Plugins that use any of it get a compiler warning. Calling the deprecated getters on Gradle’s groups and IDs, or subclassing ProblemGroup or ProblemId, also emits a deprecation warning when the build runs. Like every deprecation, the warning fails the build under --warning-mode=fail.

Create the group from the predefined hierarchy and the ID from the group:

// before
val group = ProblemGroup.create("sample-group", "Sample Group")
val id = ProblemId.create("missing-recipient", "Recipient not set", group)

// after
val group = problems.groups.others.group("Sample Group")
val id = group.problemId("Recipient not set")

Pick the predefined root group that matches what the problem is about, for example problems.groups.compilation, and create a sub-group of it or report into one of its predefined sub-groups; others is for problems that fit no other root. The name of a predefined ID is also its display name, and group names are limited to letters, digits, spaces and the characters -_.+/&'#.

Use getName() instead of getDisplayName(), both in the Problems API and in the Tooling API (org.gradle.tooling.events.problems). Until Gradle 10, getName() returns the display name given to ProblemGroup.create() or ProblemId.create(), and the name for groups and IDs from the predefined hierarchy. Gradle 10 will still send a display name, equal to the name, to Tooling API clients of earlier versions, so those clients keep working. A plugin that subclasses ProblemGroup or ProblemId must still implement getDisplayName(); mark the implementation @Deprecated to avoid the compiler warning.

ProblemGroup.getParent() in the Problems API has no replacement. The groups from problems.groups have a fixed place in the predefined hierarchy, so plugins have no need to walk it. A plugin that subclasses ProblemGroup must still implement getParent() until Gradle 10; mark the implementation @Deprecated as well. The Tooling API ProblemGroup.getParent() is not deprecated, as clients use it to show the group hierarchy.

Deprecation of restricting the KotlinDslScriptsModel to explicit scripts

The KotlinDslScriptsModel is the Tooling API model that IDEs use to provide editing assistance for Kotlin DSL scripts.

Restricting the model to an explicit set of scripts by setting the org.gradle.tooling.model.kotlin.dsl.scripts Gradle property is now deprecated and will be removed in Gradle 10. The corresponding KotlinDslScriptsModel.SCRIPTS_GRADLE_PROPERTY_NAME constant in the Tooling API is deprecated on the same schedule. Setting the property still works and emits a deprecation warning, so the behavior of such requests is unchanged in Gradle 9.x. With Isolated Projects enabled, setting the property fails the model request, as it always has.

In Gradle 10, the property will be ignored, and the model will always be built for all the Kotlin DSL scripts of the build.

Deprecation of the Kotlin DSL zipTo and unzipTo functions

The zipTo and unzipTo functions in the org.gradle.kotlin.dsl.support package have been deprecated and will be removed in Gradle 10.

To create an archive, use the Zip task type:

build.gradle.kts
tasks.register<Zip>("packageDistribution") {
    archiveFileName = "my-distribution.zip"
    destinationDirectory = layout.buildDirectory.dir("dist")

    from(layout.buildDirectory.dir("toArchive"))
}

To unpack an archive in a build script, call zipTree inside a Copy task:

build.gradle.kts
tasks.register<Copy>("unpackFiles") {
    from(zipTree("src/resources/thirdPartyResources.zip"))
    into(layout.buildDirectory.dir("resources"))
}

build.gradle.kts
abstract class UnpackTask @Inject constructor(
    private val archives: ArchiveOperations,
    private val fs: FileSystemOperations
) : DefaultTask() {
    @get:InputFile abstract val zipFile: RegularFileProperty
    @get:OutputDirectory abstract val destinationDir: DirectoryProperty

    @TaskAction
    fun unpack() {
        fs.copy {
            from(archives.zipTree(zipFile))
            into(destinationDir)
        }
    }
}

Deprecation of service injection into the parameters of a value source

The ValueSourceParameters of a ValueSource are data holders: they carry the inputs of the value source as properties and other serializable values, and Gradle isolates them before the value is obtained. Declaring an @Inject getter or constructor that takes a Gradle service on a parameters type, or on a type nested in it, is now deprecated. It still works and emits a deprecation warning in Gradle 9.x, and it will fail with an error in Gradle 10.

Such an injection was never supported, and it did not work reliably: the injected service was lost as soon as the parameters declared a property.

Deprecated: a service injected into the parameters
interface GreetingParameters : ValueSourceParameters {
    @get:Inject
    val providers: ProviderFactory
}

abstract class Greeting : ValueSource<String, GreetingParameters> {
    override fun obtain(): String = parameters.providers.gradleProperty("greeting").get()
}

val greeting = providers.of(Greeting::class) {}

The supported way is to compute the value that needs the service where the provider is created, and to pass it in as a parameter:

Instead: pass the value as a parameter
interface GreetingParameters : ValueSourceParameters {
    val greeting: Property<String>
}

abstract class Greeting : ValueSource<String, GreetingParameters> {
    override fun obtain(): String = parameters.greeting.get()
}

val greeting = providers.of(Greeting::class) {
    parameters.greeting = providers.gradleProperty("greeting")
}

To run an external process from a value source, inject ExecOperations into the ValueSource implementation itself, as described in Using External Information Sources.

Deprecation of non-required versions for plugins in a version catalog

When a plugin declared in a version catalog is applied, only its required version is used to resolve the plugin. Any prefer, strictly, or reject constraint is silently ignored, which can lead to an unexpected plugin version being selected.

Declaring a plugin version in a version catalog with constraints other than a required version is now deprecated and will become an error in Gradle 10. This includes plugins that reference such a version with version.ref, and plugins declared through the versionCatalogs {} block in a settings file.

gradle/libs.versions.toml
[versions]
my-plugin = { require = "[1.0,)", prefer = "1.5" }

[plugins]
my-plugin = { id = "com.example.my-plugin", version.ref = "my-plugin" }

To fix this, declare the version with only a required version:

gradle/libs.versions.toml
[versions]
my-plugin = "1.5"

[plugins]
my-plugin = { id = "com.example.my-plugin", version.ref = "my-plugin" }

Deprecation of implicit Ant classes on the build script classpath

Starting with Gradle 10, Ant classes will no longer be implicitly available to build scripts. This is a consequence of the deprecation of the Ant integration described below.

The most common way build scripts rely on Ant classes is filter(Map, Class) on the Copy task or on a CopySpec, which takes an Ant FilterReader such as ReplaceTokens.

To replace Ant’s ReplaceTokens filter, use filter(Transformer) to replace the tokens of each line in a single pass:

build.gradle.kts
tasks.register<Copy>("processTemplates") {
    from("src/templates")
    into(layout.buildDirectory.dir("templates"))

    val tokens = mapOf("version" to "1.0")
    inputs.properties(tokens)
    val pattern = Regex(tokens.keys.joinToString("|") { Regex.escape("@$it@") })
    filter { line: String -> pattern.replace(line) { tokens.getValue(it.value.removeSurrounding("@")) } }
}
build.gradle
tasks.register("processTemplates", Copy) {
    from("src/templates")
    into(layout.buildDirectory.dir("templates"))

    def tokens = [version: "1.0"]
    inputs.properties(tokens)
    def pattern = tokens.keySet().collect { Pattern.quote("@${it}@") }.join("|")
    filter { String line -> line.replaceAll(pattern) { String match -> tokens[match[1..-2]] } }
}

As long as no token key contains a line break, this replaces tokens the same way as ReplaceTokens. Otherwise, implement a java.io.FilterReader and pass it to filter(Map, Class), run Ant in a separate process, or include Ant on the script classpath as described below.

Manually adding Ant to the script classpath

This is a migration path for Gradle 10. Builds running on Gradle 9.x need no change. When you upgrade to Gradle 10 and want to keep using Ant’s filters, add Ant to the classpath of your build logic. If your build uses convention plugins, add Ant as a dependency of the build that contains them, for example with implementation("org.apache.ant:ant:1.10.17"). Otherwise, add Ant to the classpath configuration in the buildscript block of your build script:

build.gradle.kts
import org.apache.tools.ant.filters.ReplaceTokens

buildscript {
    repositories {
        mavenCentral()
    }
    dependencies {
        classpath("org.apache.ant:ant:1.10.17")
    }
}

tasks.register<Copy>("processTemplates") {
    from("src/templates")
    into(layout.buildDirectory.dir("templates"))
    filter<ReplaceTokens>("tokens" to mapOf("version" to "1.0"))
}
build.gradle
import org.apache.tools.ant.filters.ReplaceTokens

buildscript {
    repositories {
        mavenCentral()
    }
    dependencies {
        classpath("org.apache.ant:ant:1.10.17")
    }
}

tasks.register("processTemplates", Copy) {
    from("src/templates")
    into(layout.buildDirectory.dir("templates"))
    filter(ReplaceTokens, tokens: [version: "1.0"])
}
Before Gradle 10, this puts a second copy of Ant on the build script classpath, and Gradle’s own copy of the Ant classes takes precedence.

Call the tool directly

If you use Ant to run another tool, prefer running that tool directly instead. For example, use a JavaExec task to run its main class, or use the Worker API to call its Java API with the tool on the classpath of the work. You can also put the tool on the classpath of your build logic and call its Java API during configuration time or from a task action.

Run Ant as a separate process

If the tool you want to run has no entry point other than an Ant task, you can execute Ant in a separate Java process in a task. First, declare configurations for Ant and the tool you want to execute. Then, register the task that executes Ant, using the resolvable configuration as its classpath.

build.gradle.kts
val antTool = configurations.dependencyScope("antTool")
val antClasspath = configurations.resolvable("antClasspath") {
    extendsFrom(antTool)
}

repositories {
    mavenCentral()
}

dependencies {
    antTool("org.apache.ant:ant:1.10.17")
    antTool("org.glassfish.jaxb:jaxb-xjc:4.0.9")
}

tasks.register<GenerateJaxbClasses>("generateJaxbClasses") {
    toolClasspath.from(antClasspath)
    schema = layout.projectDirectory.file("src/main/schema/order.xsd")
    packageName = "com.example.order"
    outputDir = layout.buildDirectory.dir("generated/jaxb")
}
build.gradle

def antClasspath = configurations.resolvable("antClasspath") {
    extendsFrom(antToolScope)
}

repositories {
    mavenCentral()

    antTool("org.apache.ant:ant:1.10.17")
    antTool("org.glassfish.jaxb:jaxb-xjc:4.0.9")

    toolClasspath.from(antClasspath)

    outputDir = layout.buildDirectory.dir("generated/jaxb")
}

The task generates an Ant build file, then executes Ant with ExecOperations.javaexec().

buildSrc/src/main/java/GenerateJaxbClasses.java
@CacheableTask
public abstract class GenerateJaxbClasses extends DefaultTask {
    @Classpath
    public abstract ConfigurableFileCollection getToolClasspath();

    @InputFile
    @PathSensitive(PathSensitivity.RELATIVE)
    public abstract RegularFileProperty getSchema();

    @Input
    public abstract Property<String> getPackageName();

    @OutputDirectory
    public abstract DirectoryProperty getOutputDir();

    @Inject
    protected abstract ExecOperations getExecOperations();

    @TaskAction
    public void generate() throws IOException {
        File buildFile = new File(getTemporaryDir(), "build.xml");
        Files.writeString(buildFile.toPath(), """
            <project name="jaxb">
                <taskdef name="xjc" classname="com.sun.tools.xjc.XJCTask"/>
                <target name="generate">
                    <xjc schema="${schema}" destdir="${destdir}" package="${package}"/>
                </target>
            </project>
            """);

        getExecOperations().javaexec(spec -> {
            spec.classpath(getToolClasspath());
            spec.getMainClass().set("org.apache.tools.ant.Main");
            spec.args(
                "-buildfile", buildFile.getAbsolutePath(),
                "-Dschema=" + getSchema().get().getAsFile().getAbsolutePath(),
                "-Ddestdir=" + getOutputDir().get().getAsFile().getAbsolutePath(),
                "-Dpackage=" + getPackageName().get(),
                "generate"
            );
        });
    }
}

Task logging listeners are now stored in the Configuration Cache

Standard output and error listeners registered on a task’s logging manager during configuration (for example via LoggingOutput.addStandardOutputListener or LoggingOutput.addStandardErrorListener) are now stored in the Configuration Cache and re-registered on a cache hit, so they receive the task’s output as they would without the Configuration Cache.

Previously, these listeners were silently discarded and never received output when the Configuration Cache was used.

A listener that cannot be serialized is now reported as a Configuration Cache problem instead of being silently dropped, which may cause a build that previously worked to fail. If your build registers such a listener and the listener is nonessential, you can opt out, restoring the previous behavior where listeners are dropped on a cache hit, and no problem is reported by setting:

This property is a temporary opt-out, deprecated since Gradle 9.9 and scheduled for removal in Gradle 11.

Kotlin object singletons keep their identity in the Configuration Cache

If your build stored mutable state on a Kotlin object, that state is no longer restored on a cache hit; move it elsewhere.

A Kotlin object (including companion object declarations) stored in the Configuration Cache is now restored as the same singleton instance. As a consequence, only the singleton’s identity is restored, not any mutable state it may hold.

Previously, each object was serialized as a regular bean and rebuilt as a new instance on a cache hit, so deserialized === TheObject was false. If you relied on mutable state surviving a cache hit, move it into a task property or another bean type that is serialized by value.

Common cases that previously failed and now warn:

  • Cross-platform builds where a Unix-style absolute path such as /opt/jdk-24 is treated as relative on Windows.

  • Relative paths committed to gradle.properties in version control.

Deprecation of implicit opt-in to parallel model building

Parallel model building lets Tooling API clients (most commonly IDEs during project synchronization) build project models in parallel. Historically, it had no dedicated control and was enabled implicitly whenever parallel execution (org.gradle.parallel=true or --parallel) was enabled.

Gradle 9.4.0 introduced the dedicated org.gradle.tooling.parallel property to control parallel model building explicitly. When that property is not set, its value is currently derived from org.gradle.parallel to preserve backward compatibility.

Relying on this implicit behavior is now deprecated. When org.gradle.parallel is enabled and org.gradle.tooling.parallel is not set explicitly during model building, Gradle emits a deprecation warning. In Gradle 10, the two properties will become independent, and enabling org.gradle.parallel without an explicit value for org.gradle.tooling.parallel during model building will be an error.

To avoid the warning and prepare for Gradle 10, set org.gradle.tooling.parallel explicitly to either true or false, for example in gradle.properties:

org.gradle.tooling.parallel=true

Additionally, the transitional system property org.gradle.tooling.parallel.ignore-legacy-default (used by some IDEs during sync to opt out of the legacy default) will no longer be honored in Gradle 10. Once org.gradle.parallel and org.gradle.tooling.parallel are independent, the flag is redundant, so Gradle 10 simply ignores it. No action is required in Gradle 9.x; if you set it explicitly, you can remove it when upgrading to Gradle 10.

Deprecation of starting external processes at configuration time with ExecOperations and Java/Groovy standard APIs

Starting an external process at configuration time with ExecOperations or the Java and Groovy standard APIs directly is now deprecated. This includes:

  • ExecOperations.exec and ExecOperations.javaexec.

  • java.lang.ProcessBuilder.start() and ProcessBuilder.startPipeline(…​).

  • java.lang.Runtime.exec(…​) (all overloads).

  • The Groovy process helpers String.execute(…​), String[].execute(…​), and List.execute(…​).

This does not affect uses of the ProviderFactory.exec / ProviderFactory.javaexec providers (providers.exec / providers.javaexec) or a ValueSource that runs a process inside, those remain the supported way to run a process at configuration time.

Starting an external process at configuration time in any of the deprecated ways is already an error when the Configuration Cache is enabled. Because the Configuration Cache will be enabled by default in Gradle 10, Gradle now deprecates unsupported behaviors even when the Configuration Cache is not currently enabled.

Migrate to one of the following, in order of preference:

  1. Move the process execution into a task, so it runs at execution time and benefits from build caching, up-to-date checks, and work avoidance. Use an Exec or JavaExec task, or a custom task that injects ExecOperations and runs the process in its task action.

  2. For simple cases, use providers.exec / providers.javaexec. Prefer wiring the returned provider lazily to task inputs, and call get() only as a last resort.

  3. For more complex output processing, use a ValueSource that injects ExecOperations (or uses java.lang.ProcessBuilder directly). The same guidance about wiring the provider lazily to task inputs applies.

This behavior will become an error in Gradle 11.

Potential breaking changes

Resilient sync reports failed operations

Tooling API clients that query models through the incubating BuildController.fetch(…​) method perform a resilient sync: failures are attached to each FetchModelResult instead of aborting the operation.

Previously, such an operation could complete successfully even when some of these model builds failed. The failures were reported only through FetchModelResult.getFailures(), and the client still received a successful result.

Starting in Gradle 9.7.0, the operation is reported as failed when any part of it fails: ResultHandler.onFailure(…​) is called, and a blocking run() throws, even though the partial models have already been delivered. Because a single BuildAction loses its result in that case, clients should use a phased build action and read the partial models from the intermediate result handlers.

This aligns resilient sync with the reporting of getModel(…​) and findModel(…​), and of task and configuration failures, so a sync in which something failed is no longer reported as successful.

Checksum files are no longer published for signature files

When publishing to Maven or Ivy repositories, Gradle no longer publishes checksum files (such as .sha1 and .md5) for signature files like .asc and .sig.

A signature is itself an integrity artifact, so a checksum of a signature provides no additional protection, and the standard Maven publishing tooling does not publish these files either. The signature files themselves continue to be published unchanged; only their checksum files are no longer produced.

The project cache directory is no longer watched

Gradle no longer watches the project cache directory (the .gradle directory in the root project, or a custom location set with --project-cache-dir). Because Gradle is the only writer to this directory, it keeps the virtual file system up to date directly, without relying on OS file system events.

As a result, a custom project cache directory no longer disables file system watching. Previously, --project-cache-dir (or org.gradle.projectcachedir) was incompatible with watching: passing --watch-fs alongside it failed the build, and leaving watching at its default silently disabled it. File system watching now follows the usual rules regardless of where the project cache directory is located.

This applies to the project cache directory itself. Source-dependency check-outs, which live under the project cache directory but whose contents can change externally, remain watched as regular build directories.

println(foo) // Resolved through hierarchy — now deprecated

This implicit inheritance is deprecated and will be removed in Gradle 10.

Implicit hierarchy lookup creates hidden coupling between projects, makes builds harder to reason about (a typo silently resolves to an ancestor’s definition instead of failing), and is fundamentally incompatible with Isolated Projects.

Here is a full list of affected APIs and DSL constructs:

  • Dynamic references such as a bare foo or bar() in Groovy DSL

  • Kotlin DSL property delegates such as val foo: String by project

  • Explicit API calls on the Project instance or in a build script:

    • findProperty("foo")

    • property("foo")

    • hasProperty("foo")

    • getProperties()

To migrate, choose the approach that best fits your use case:

  • Build-wide configuration values — declare them in gradle.properties at the root, and read them in subprojects via providers.gradleProperty("name"). They become typed Provider<String> values and are available everywhere without any walking.

  • Plugin defaults / shared logic — extract into a convention plugin applied to each subproject. Each subproject gets its own configuration; nothing crosses project boundaries.

  • Explicit reference to an ancestor’s value — write rootProject.ext.foo (or parent.ext.foo) in the child build script. This is a transitional fix: it preserves the cross-project coupling and is therefore not Isolated Projects compatible, but it removes the deprecation warning and makes the dependency explicit.

If you need to keep the original walking semantics, the following helper can be added to a build script or convention plugin:

child/build.gradle.kts
tailrec fun Project.findExtraInHierarchy(name: String): Any? {
    if (extra.has(name)) return extra[name]
    val ancestor = parent ?: return null
    return ancestor.findExtraInHierarchy(name)
}
child/build.gradle
def findExtraInHierarchy(Project project, String name) {
    if (project == null) return null
    if (project.ext.has(name)) return project.ext.get(name)
    return findExtraInHierarchy(project.parent, name)
}

Deprecation of getProperties()

The following usages of getProperties() have been deprecated and will be removed in Gradle 10:

  • Calling getProperties() (or accessing the properties property) on a build script, settings script, or init script. This is a separate API on the script base class, but has the same problems.

This method, which historically existed for convenience, makes build logic harder to understand and navigate due to the untyped nature of the properties and the fact that they are sourced from many different locations and containers. Deprecation of undeclared Artifact Transform execution by tasks

Invoking an Artifact Transform from a task that does not declare the resolution as a task input is now deprecated and will become an error in Gradle 10.

With the Configuration Cache, if an Artifact Transform is not properly declared as an input, and requires a producer project that no other scheduled task requires, the producer may not be scheduled and may be unreachable. This can manifest as project <name> not found errors.

Now, a deprecation is emitted for each task that executes an Artifact Transform that is not declared as an input. This provides an early warning for build scenarios that were only working "by accident".

To fix this warning, declare the resolution triggering the Artifact Transform as a task input. You can do this by exposing a configurations' files collection through a typed @InputFiles property on a custom task type. If you must use an ad-hoc task, supply myCustomConfiguration.files to inputs.files(…​), or, when consuming an ArtifactCollection, supply ArtifactCollection.getArtifactFiles(). In the common case, both of these methods wire the transform steps into the execution plan so the task is recognized as a declarer of the transform.

Declaring a transformed FileCollection view as a task input:

val view = configurations["implementation"].incoming.artifactView {
    attributes.attribute(color, "green")
}.files

// Deprecated: the doLast reads view.files without declaring view as a task input.
tasks.register("consume") {
    doLast {
        println("result = ${view.files.map { it.name }}")
    }
}

// Recommended: expose the FileCollection through a typed @InputFiles property on a custom task type.
abstract class Consume : DefaultTask() {
    @get:InputFiles
    abstract val colored: ConfigurableFileCollection

    @TaskAction
    fun run() {
        println("result = ${colored.files.map { it.name }}")
    }
}

tasks.register<Consume>("consume") {
    colored.from(view)
}

Declaring a transformed ArtifactCollection view as a task input — note that declaring the raw Configuration (inputs.files(configurations["compile"])) is NOT enough, because it only schedules the source artifacts, not the transforms:

val artifacts = configurations["compile"].incoming.artifactView {
    attributes { attribute(usage, "transformed") }
}.artifacts

// Deprecated: declaring the raw configuration doesn't wire the transform.
tasks.register("show") {
    inputs.files(configurations["compile"])
    doLast {
        println("files: ${artifacts.map { it.file.name }}")
    }
}

// Recommended: declare the transformed artifact view's artifactFiles as the input.
tasks.register("show") {
    inputs.files(artifacts.artifactFiles)
    doLast {
        println("files: ${artifacts.map { it.file.name }}")
    }
}

How declaration is detected

Gradle determines whether a task has declared a transform output as an input by walking the task’s transitive dependency subgraph in the execution plan after the work graph is fully built. Any transform step reachable from the task through dependency edges, without crossing into another task, is considered declared by that task. This covers chained transforms, @InputArtifactDependencies feeds across components, and componentFilter-restricted artifact views uniformly.

If you write inputs.files(view), inputs.files(artifacts.artifactFiles), or expose the collection through a typed @InputFiles property, Gradle’s input wiring places the corresponding transform nodes into the task’s dependency successors, and the post-graph walk will recognise the task as a declarer. Declaring through dependsOn(taskA) on another task that itself declares the input does NOT count: only direct declaration by the task that performs the query counts.

Deprecation of buildNeeded and buildDependents tasks

The buildNeeded and buildDependents tasks from the Java plugins are deprecated and will be removed in Gradle 10.

buildNeeded builds the current project along with all projects it depends on. buildDependents does the opposite: it builds the current project and all projects that depend on it. These tasks were introduced back in Gradle 0.8. Their implementation is incompatible with Configure on Demand and Isolated Projects, and the tasks themselves are too rigid to cover the range of use cases users actually need. Existing Gradle functionality covers these use cases, so rather than rework the tasks, we are removing them.

buildNeeded depends on the current project’s build task and on the buildNeeded task of each project that appears as a direct dependency in the testRuntimeClasspath configuration. Because those buildNeeded tasks depend on each other, the result is that the entire project dependency closure is built.

Depending on what you were using buildNeeded for, one of the following may replace it:

  • If you only need to build or test a specific project, run that task directly (e.g., ./gradlew :proj:build) and let Gradle resolve its task dependencies automatically.

  • For running tests across all projects the current project depends on, use test report aggregation.

  • For plugin authors and advanced build logic, use Artifact Views to select artifacts from projects in a dependency graph and wire their producer tasks as dependencies.

There is no direct replacement for buildDependents. For most workflows, running all tasks with a given name (e.g., ./gradlew test) combined with up-to-date checks and build caching will skip work for unaffected projects, at the cost of configuring all projects.

Potential breaking changes

ProjectBuilder now enforces consistent build-scoped locations

ProjectBuilder allows you to configure a specific project directory for tests. While project.projectDir and project.rootDir have always respected this setting, project.layout.settingsDirectory previously did not. This discrepancy could cause file resolution to inadvertently escape the project directory.

Gradle now anchors the settings search directly to the configured project directory. This ensures that layout.settingsDirectory, projectDir, and rootDir all point to the same consistent location. Projects created via ProjectBuilder are now better isolated from the host build environment.

If your tests specifically relied on layout.settingsDirectory pointing to an external location, they will need to be adjusted. Even if you do not use settingsDirectory directly, you may still observe changes in file resolution. Previously, dependency management files could be "leaked" into the test from the host build environment; this is no longer the case.

For more details see the related issue.

The java-gradle-plugin plugin now adds the gradleApi() dependency to the compileOnlyApi scope

The gradleApi() dependency is now added to the compileOnlyApi scope instead of the api scope. This prevents the gradleApi() from leaking into the runtime classpath of other dependents of the plugin project.

This might break projects that were implicitly relying on the gradleApi() being on the compilation or runtime classpath. If this is the case, add a gradleApi() dependency to the appropriate scope to restore the previous behavior.

For most plugin projects, this change should be transparent as:

  • at compilation time, the plugin project will get the gradleApi()

  • the default test source set will also automatically get the gradleApi() dependency on the compilation and runtime classpaths

If any additional test source set is used (e.g., integration tests), the plugin extension offers the plugins.testSourceSet method to register the source set for automatic management. If this cannot be done, a regular declaration of the gradleApi() dependency on the test source can be used as well.

Stricter validation for published plugins

For plugin builds that apply any of the com.gradle.plugin-publish, ivy-publish, or maven-publish plugins, Gradle now automatically enables stricter validation of plugin code.

In order not to break your builds, this does not apply to local plugins (in buildSrc or included builds containing build logic). However, we encourage you to always enable stricter validation:

build.gradle.kts
tasks.validatePlugins {
    enableStricterValidation = true
}

CodeNarc compilation classpath is set by default

The CodeNarc plugin now automatically populates the compilationClasspath of a CodeNarc task with the compile classpath of its associated source set.

CodeNarc offers Enhanced Classpath Rules (like UnusedImport or DuplicateImport) that require the project’s compiled classes and dependencies to be analyzed for full accuracy. Previously, you had to wire this up manually. Now, it works out of the box.

This change introduces a task dependency. The CodeNarc task must now wait for the compile task to finish so it can access the compiled classes.

If you do not use enhanced rules and want to restore parallel execution, you can manually empty the compilationClasspath:

build.gradle.kts
plugins {
    id("groovy")
    id("codenarc")
}

tasks.withType<CodeNarc>().configureEach {
    // Override the default compilation classpath
    compilationClasspath = files()
}

If your build relies on a custom configuration for the compilationClasspath of a CodeNarc task, you will need to continue explicitly setting it to override the new default behavior.

System property priority for Wrapper execution has changed

The priority of system properties passed to the Gradle Wrapper now correctly follows the documented order of precedence. In previous versions, properties defined in gradle.properties files could unexpectedly override those passed via the command line.

If a property is defined in multiple locations, Gradle now strictly honors the following hierarchy (from highest to lowest):

Deprecation of DomainObjectCollection.findAll(Closure)

The findAll(Closure) method on Gradle collections is now deprecated and scheduled for removal in Gradle 10.0.0.

This method relies specifically on Groovy types and eagerly evaluates the contents of the container.

To fix this, use the similar DomainObjectCollection.matching(Spec). While not a direct replacement for findAll, matching is lazy, it returns a new collection that only filters elements as they are actually needed by the build:

// Deprecated:
def checkTasks = tasks.findAll { it.name.startsWith("check") }

// Recommended:
def checkTasks = tasks.matching { it.name.startsWith("check") }

Deprecation of apply false in precompiled script plugins

The use of apply false within precompiled script plugins is now deprecated and will result in an error in Gradle 10.0.0.

In a precompiled script, the plugins {} block behaves differently than in a standard build script. Currently, if you write apply false, Gradle applies the plugin anyway. This creates confusion because the syntax suggests you are merely adding a plugin to the classpath without activating it, which is not what actually happens.

The fix depends on whether you actually want the plugin to be active in your precompiled script:

  • If you want to use the plugin: Remove the apply false statement.

  • If you do NOT want to use the plugin: Delete the line entirely.

my-plugin.gradle.kts
plugins {
    // Deprecated (and misleading, as it is still applied)
    id("org.gradle.test-retry") apply false
    // The plugin will still be on the classpath,
    // but it will not be applied as part of this precompiled script plugin.

    // Recommended: Either remove 'apply false' to keep using it,
    // or delete the line to stop using it.
    id("org.gradle.test-retry")
}

Deprecation of version in precompiled Settings script plugins

The use of version within precompiled Settings script plugins is now deprecated and will become an error in Gradle 10.0.0.

In precompiled scripts, version has no effect. The plugin version is already fixed by the script’s own build file; declaring it again inside the script is ignored and causes confusion about which version is actually in use.

To fix this, remove the .version() or version "…​" call from the plugins {} block:

my-plugin.settings.gradle.kts
plugins {
    // Deprecated:
    id("org.gradle.test-retry") version "x.y.z"
    // Recommended:
    id("org.gradle.test-retry")
}

Deprecation of Dependencies.getProject() method

The getProject() method on Dependencies has been deprecated and will be removed in Gradle 10.0.0.

Dependencies is used to configure dependencies in test suites. Previously, getProject() was used by Gradle internally to reference the current project. While never intended for public use, it could be used unintentionally in build scripts.

For example, the following configuration accidentally invokes the deprecated method because project.path resolves against the Dependencies object rather than the top-level Project object:

testing {
    suites {
        val integrationTest by registering(JvmTestSuite::class) {
            dependencies {
                implementation(project(project.path)) // `project.path` accesses `Dependencies.getProject()`
            }
        }
    }
}

The configuration above may now fail to compile with an error in 9.5.0 if -Werror is set.

To depend on the current project, use the project() method without arguments. This syntax is the idiomatic way to reference the project in both test suites and standard dependencies {} blocks:

testing {
    suites {
        val integrationTest by registering(JvmTestSuite::class) {
            dependencies {
                implementation(project())
            }
        }
    }
}

Potential breaking changes

Referential equality is not guaranteed for Project instances

Instances of Project type representing the same logical Gradle project do not provide any guarantee of being equal by reference (== in Java, === in Kotlin). However, historically it was possible to observe that such Project instances were exactly the same.

In Gradle 9.3.0, Project instances (for the same logical project) can be different with respect to the referential equality, even if obtained within the same context, e.g., in the same build script. This change is necessary to facilitate future performance improvements of Gradle. The Project.equals() equality behavior remains unchanged.

Avoid referential equality in Kotlin:

build.gradle.kts
// DON'T do this
project.rootProject === project.parent

Avoid referential equality in Groovy:

build.gradle
// DON'T do this
project.rootProject.is(project.parent)

Avoid referential equality in Java:

MyPlugin.java

// DON'T do this
project.getRootProject() == project.getParent();

In general, it is better to check project equality via Project.getPath() or Project.getBuildTreePath() for composite-build support. The paths are also better suited to be keys in data structures, like maps.

TestNG output may change when using versions before 6.9.13.3

As part of the AbstractTestTask refactoring, Gradle’s integration with TestNG has been updated. Gradle now relies on a correctly functioning IClassListener to report the hierarchy of test classes and methods.

When using TestNG versions earlier than 6.9.13.3, this can lead to different or degraded output:

  • With older versions, class information may be lost. For example, output that previously looked like: org.gradle > TestClass > ok may now be reported simply as: ok.

  • For TestNG versions from 6.9.10 up to (but not including) 6.9.13.3, the IClassListener API exists but is broken. This can result in even worse output, such as empty or missing names.

To get correct and stable output, we recommend upgrading to TestNG 6.9.13.3 or newer.

Deprecation of publishing dependencies on unpublished projects

When publishing a project, Gradle resolves project dependencies to the coordinates of the target project’s publication. If the target project has no publication, Gradle currently resolves the dependency silently using that project’s group, name, and version.

Starting with Gradle 10, this behavior is deprecated. Gradle will no longer silently ignore the absence of a publication. Publishing a project that depends on another project without a publication will be forbidden and will cause the build to fail. This change prevents publishing broken metadata with dependency coordinates that cannot be resolved.

The example below demonstrates a build that triggers the deprecated behavior:

build.gradle.kts
plugins {
    id("java-library")
    id("maven-publish")
}

group = "com.example"
version = "1.0.0"

dependencies {
    api(project(":other"))
}

publishing {
    publications {
        create<MavenPublication>("maven") {
            from(components["java"])
        }
    }
}
other/build.gradle.kts
plugins {
    id("java-library")
}

group = "com.example"
version = "1.0.0"

To avoid this deprecation, ensure that all project dependencies of published projects are also published. In the example above, applying the maven-publish plugin and configuring a publication in the :other project resolves the issue:

other/build.gradle.kts
plugins {
    id("java-library")
    id("maven-publish")
}

group = "com.example"
version = "1.0.0"

publishing {
    publications {
        create<MavenPublication>("maven") {
            from(components["java"])
        }
    }
}

Deprecation of using module coordinates to depend on the current project

Starting with Gradle 10, declaring a dependency on the current project using module coordinates (group, name, version) will no longer resolve to that project. Instead, Gradle will attempt to resolve that dependency from a repository.

The example below demonstrates the change in behavior:

my-project/build.gradle.kts
group = "com.example"
version = "1.0.0"

val deps = configurations.dependencyScope("deps")
val classpath = configurations.resolvable("classpath") {
    extendsFrom(deps.get())
    attributes.attribute(Category.CATEGORY_ATTRIBUTE, objects.named(Category.LIBRARY))
}

val elements = configurations.consumable("elements") {
    attributes.attribute(Category.CATEGORY_ATTRIBUTE, objects.named(Category.LIBRARY))
}

dependencies {
    // In Gradle 9.x, this dependency resolves to the `elements` configuration.
    // In Gradle 10, this dependency will attempt to resolve from a repository.
    deps("com.example:my-project:1.0.0")
}

To continue depending on the current project, use a project dependency:

my-project/build.gradle.kts
dependencies {
    // Declare a dependency on the current project to continue resolving
    // to the current project.
    deps(project)
}

Deprecation of multi-string dependency notation

In an effort to simplify and standardize the Gradle API, the multi-string dependency notation used in dependency management has been deprecated and will no longer be permitted in Gradle 10. Gradle will primarily accept dependency declarations in the form of a single string, with each dependency coordinate separated by a colon.

Below are examples of the deprecated multi-string notation:

build.gradle.kts
dependencies {
    implementation(group = "org", name = "foo", version = "1.0")
    implementation(group = "org", name = "foo", version = "1.0", configuration = "conf")
    implementation(group = "org", name = "foo", version = "1.0", classifier = "classifier")
    implementation(group = "org", name = "foo", version = "1.0", ext = "ext")
}

testing.suites.named<JvmTestSuite>("test") {
    dependencies {
        implementation(module(group = "org", name = "foo", version = "1.0"))
    }
}
build.gradle
dependencies {
    implementation(group: 'org', name: 'foo', version: '1.0')
    implementation(group: 'org', name: 'foo', version: '1.0', configuration: 'conf')
    implementation(group: 'org', name: 'foo', version: '1.0', classifier: 'classifier')
    implementation(group: 'org', name: 'foo', version: '1.0', ext: 'ext')
}

testing.suites.test {
    dependencies {
        implementation(module(group: 'org', name: 'foo', version: '1.0'))
    }
}

These declarations should be replaced with the single-string notation:

build.gradle.kts
dependencies {
    implementation("org:foo:1.0")
    implementation("org:foo:1.0") {
        targetConfiguration = "conf"
    }
    implementation("org:foo:1.0:classifier")
    implementation("org:foo:1.0@ext")
}

testing.suites.named<JvmTestSuite>("test") {
    dependencies {
        implementation("org:foo:1.0")
    }
}
build.gradle
dependencies {
    implementation("org:foo:1.0")
    implementation("org:foo:1.0") {
        targetConfiguration = "conf"
    }
    implementation("org:foo:1.0:classifier")
    implementation("org:foo:1.0@ext")
}

testing.suites.test {
    dependencies {
        implementation("org:foo:1.0")
    }
}

In some cases, a complete single-string notation may not be known up front. Instead of concatenating the coordinates into a new string, it is possible to use a DependencyFactory to create Dependency instances directly from the individual components:

build.gradle.kts
val group = "org"
val artifactId = "foo"
val version = "1.0"

configurations.dependencyScope("implementation") {
    dependencies.add(project.dependencyFactory.create(group, artifactId, version))
}
build.gradle
def group = "org"
def artifactId = "foo"
def version = "1.0"

configurations.dependencyScope("implementation") {
    dependencies.add(project.dependencyFactory.create(group, artifactId, version))
}

Deprecation of JavaForkOptions.setAllJvmArgs()

The setAllJvmArgs() method on JavaForkOptions and, by inheritance, on JavaExecSpec has been deprecated and will be removed in Gradle 10.0.0.

Instead, to overwrite existing JVM arguments, use:

  • JavaForkOptions.jvmArgs()

  • JavaForkOptions.setJvmArgs()

  • Provide a CommandLineArgumentProvider to add arguments via JavaForkOptions.getJvmArgumentProviders()

Note that setAllJvmArgs() method on JavaForkOptions cleared all fork options before setting jvmArgs. The properties cleared included:

  • System properties configured via JavaForkOptions.systemProperties

  • JVM argument providers configured via JavaForkOptions.jvmArgumentProviders

  • Argument providers configured via JavaExecSpec.argumentProviders

  • Memory settings configured via JavaForkOptions.minHeapSize and JavaForkOptions.maxHeapSize

  • All other JVM arguments configured via JavaForkOptions.jvmArgs

  • The assertion and debug flags configured via JavaForkOptions.enableAssertions and JavaForkOptions.debug

If the arguments you provide to setJvmArgs() or jvmArgs() depend on any of the above properties being cleared, you will need to manually clear them.

Consider the following snippets for examples of how to implement this change:

build.gradle.kts
plugins {
    id("java")
}

tasks.register<JavaExec>("myRunTask") {
    jvmArgumentProviders.clear() // Clear existing JVM argument providers
    maxHeapSize = null // Clear max heap size
    jvmArgs = listOf("-Dfoo", "-Dbar") // Set new JVM arguments
}
build.gradle
plugins {
    id("java")
}

tasks.named('myRunTask', JavaExec) {
    jvmArgumentProviders.clear() // Clear existing JVM argument providers
    maxHeapSize = null // Clear max heap size
    jvmArgs = ["-Dfoo", "-Dbar"] // Set new JVM arguments
}
